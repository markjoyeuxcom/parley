Parley
Operator's Manual

A local-first macOS workbench for governed agent work. Parley drives Claude Code and Codex through their own CLIs — against the subscriptions you already pay for — and puts structure, verification and a permanent record around what they do.

Covers the development build · July 2026 · See README.md for per-surface rationale and AGENTS.md for the engineering guide

1 · What Parley is

Parley is a workbench, not a chatbot. It runs the two agent CLIs you already have — claude and codex — and arranges them into shapes that produce things you can trust: adversarial debates that end in a recorded verdict, codebase reviews where findings are cross-examined against the code, execution pipelines where every write sits behind your recorded approval and every diff is reviewed by the vendor that didn't write it, and autonomous loops with caps an agent cannot see or talk past.

Three commitments run through everything:

  • Your subscriptions, never an API key. Every model call goes through your local CLI, signed in to your own account. Parley has no API-key code path at all.
  • Everything on the record. Sessions, verdicts, dissent, findings, dispositions, approvals, run activity, landings — all of it lands in a local SQLite database and none of it leaves your machine.
  • No agent certifies its own work. Tests are run by Parley itself and read by exit code; reviews come from the model family that didn't write the diff; disagreement lowers recorded confidence instead of being smoothed away.

2 · First run

Requirements

  • macOS on Apple Silicon
  • Claude Code and/or Codex CLI, installed and signed in
  • Node 24+ to build

Build and start

npm install        # also rebuilds node-pty against Electron's ABI
npm run dev        # the development app
npm run package:mac  # a signed-runtime .dmg for Apple Silicon

The toolbar shows each CLI's health at startup, because "installed but not signed in" is the most common reason a session produces nothing. macOS starts GUI apps with a minimal PATH; Parley reads your login shell's PATH at launch so Homebrew and npm -g installs are found.

Try it without spending anything

PARLEY_MOCK=1 npm run dev

Deterministic mock adapters stand in for both CLIs — every flow is walkable, no quota is spent, and the app makes the substitution unmissable (§15).

3 · The four surfaces

SurfaceKeysReach for it when
Grid⌘1 You're driving. Live terminals, real CLI sessions, no governance.
Parley⌘2 A decision needs a debate, or a codebase needs findings you can act on without re-verifying each one. Plans live here too.
Loops⌘3 "Done" is machine-checkable and the work converges.
Repos⌘4 You want the repository — its backlog, its plans across every session, its foreman — answering for itself in one place.

⌘K opens the command palette from anywhere: jump between surfaces, start a debate or review directly. The titlebar's Auto / Light / Dark control cycles appearance, and the inbox icon beside it is the holds queue (§10).

4 · Grid ⌘1

Up to sixteen live terminals in a splittable, resizable layout. A pane is a shell or a real interactive claude / codex session — the actual CLI with its own prompts and TUI, not a re-hosted imitation.

  • Panes are multi-folder. Each keeps the folder it started in; a split inherits its neighbour's; the toolbar only decides where the next pane opens. Working across two repositories at once is the normal case.
  • Skills are reusable prompt packs on the rail along the bottom. Drag one onto an agent pane and it is typed into that live session, with all the context the session already has.
  • Saved layouts restore the arrangement — pane kinds, split tree, folders. Shells reopen immediately; agent panes come back as one-click placeholders, so no CLI session starts against your subscription without you asking.

The Grid is ungoverned. A pane has the CLI's own permission prompts and none of Parley's — no single-use approval, no deterministic verification, no independent review. Right for small edits you're watching; wrong for a change you'll ship. Nothing here persists except scrollback and the layout.

5 · Debates & reviews ⌘2

Sessions are read-only by invariant — they argue, audit and record; they never write. Two agents from different model families hold the seats by default, and a session can seat up to four participants.

Debate

Put a decision to both vendors: one stakes a position, the other attacks the load-bearing assumption, they refine under pressure, then converge. What makes it more than asking one model twice:

  • Neither side writes the verdict. Both record verdicts independently and Parley merges them — and disagreement lowers the recorded confidence. Two advisors at 90% certainty who score the option ten points apart have not produced a confident answer, and the report says so.
  • Dissent is preserved verbatim. The losing side's objection is the most perishable output of an adversarial session, so it is stored and shown in full.
  • You can interject mid-session — address both sides, or whisper to one. The other side never learns it happened, which is how you test whether a position survives private pressure.

A low confidence score is a success: it tells you the decision is genuinely contested, which is exactly what one model's self-agreement cannot.

Codebase review

One agent maps the architecture, the other audits independently, then they cross-examine each other's findings. A finding only reaches confirmed if the other agent corroborated it against the code, and a confirmed claim with no file-and-line evidence is downgraded automatically. Dismissed findings are kept — "investigated and cleared" is worth as much as a finding.

Scope the brief, or it goes shallow. "Audit error handling in the sync layer" produces findings worth having; "review this repository" produces breadth without depth. Reviews are read-only and have no memory of previous reviews — recurring work belongs to the backlog (§11).

Confirmed findings don't stop at the report: they file automatically onto the repository's backlog as open items, with provenance back to the session.

6 · Findings & the gate

Every blocking finding recorded against a plan — by its audit, its milestone reviews, or a review session — lands in the findings ledger and stays open until a human disposes of it: resolved, accepted risk, or not a finding, each with a note.

The ledger is a gate, not a list. While blocking findings are open, the approval dialog refuses to arm — it shows the findings with inline disposition controls (and a bulk control for a batch), so clearing the gate and recording your reasoning are the same motion. Accepted risks are ingested to the backlog rather than forgotten.

Fail-closed is deliberate. If the ledger cannot be loaded, the gate disables rather than un-gates. Unknown is treated as blocking, never as clear.

7 · Audited execution

A verdict can become work, through a pipeline whose roles are deliberately split:

plan (read-only)
  → audited by the other vendor (read-only)
    → the planner answers that audit, and corrects the plan
      → your approval, single-use
        → execute one milestone (write)
          → deterministic tests, run by Parley itself
            → the diff reviewed by the vendor that did not write it
              → rejection handed back to the executor, up to twice
  • The planner answers its own audit. Every audit finding gets a disposition and the plan is corrected before you ever approve — otherwise what executes is the original draft with an unread critique attached.
  • Agents may ask, once. A brief with a genuine fork stops on a question instead of guessing; your answer (⌘↵) resumes the planner, which still holds its own draft.
  • Approval is per-milestone, recorded, and spent the moment the run starts. Re-running asks again. Before you spend anything, the dialog runs a preflight — if the files a milestone would create already exist (usually a prior interrupted attempt), it says so and offers Adopt & verify instead.
  • Completion needs both checks. Green tests and a pass from the independent reviewer. A rejection goes back to the executor inside the same run — it receives a critique, not a restatement — bounded to two rounds before the plan says a person is needed.
  • Adopt & verify records honestly: verification and independent review, but the trail marks the milestone adopted, never implying Parley authored code it merely inspected.

Interruptions are cheap

A crashed or stopped milestone keeps its run state — the remediation round, the reviewer's critique, both agents' resumable sessions, the exact baseline — and can be resumed with a fresh approval: the executor continues from a critique instead of re-executing, and finished work is verified rather than redone. A running milestone has a stop button. A run that goes silent surfaces as a stalled hold with a read-only cross-vendor inspection attached; nothing is ever aborted automatically.

Five post-verdict workflows: implementation, validation, remediation, migration, research.

8 · Worktrees & landing

Where the work lands is a choice made at plan creation:

  • In the checkout — milestones write into your tree and are left uncommitted for you. Simple, visible, immediate.
  • In a worktree — every milestone executes in an isolated git worktree on a per-plan branch. Parley commits each passing milestone there (the agent still never commits), and your checkout is untouched until you land the branch.

Landing is fast-forward only, behind its own recorded single-use approval, and git itself refuses if your checkout moved or dirt would be overwritten — a refusal parks as a merge-blocked hold naming the branch, whose commits are the surviving copy of the work. After a successful landing, the last milestone's test command runs once in your checkout as a smoke check; a red result flags the landed plan in the holds queue.

Worktrees live under the app's own support directory, are reconciled at startup, and are never deleted by reconciliation — a vanished directory is recovered from its surviving branch. If a worktree needs dependencies, give the plan a setup command (for example npm ci); it runs once when the worktree is created, shell-free like every command Parley spawns.

9 · Loops ⌘3

Autonomous runs that stop for reasons you can check.

  • Caps are enforced by Parley before each iteration — iterations, wall-clock, and reported spend. The agent cannot see them or talk past them. Hitting one is reported as exhausted, never as success.
  • The exit condition is never self-reported. Either Parley runs a real command and reads its exit code, or the other vendor's model inspects the repository.
  • A kill switch aborts the in-flight CLI immediately.

A write-capable loop is a weaker guarantee than a milestone. The pipeline requires green tests and an independent review; a loop requires only its exit condition — and a writing agent whose exit is the test suite can in principle reach green by weakening a test. Prefer read-only loops; for changes that matter, use the pipeline. On subscriptions the spend cap barely bites, so iterations and wall-clock do the real work.

10 · Holds — what is waiting on you

Everything that blocks on a human decision queues in one place: a planner's question, a milestone ready to approve, an approval gated by open findings, a branch ready to land, a failed milestone, a stalled run, an exhausted loop, a backlog with proposals to triage, a foreman proposal, a verified fresh build of Parley itself.

  • The titlebar count is decisions only. Notices sit inside the panel without wearing on the badge.
  • Each hold notifies once, ever — one macOS notification when it first appears, never again, including across restarts.
  • Opening a hold lands you at its exact control — a milestone hold opens the approval dialog itself, a backlog hold opens the right repository on the right tab.
  • Decision holds clear only by acting — answering, approving, landing. The app refuses to acknowledge them away: a dismissible "waiting on your answer" clears the badge while the plan stays parked, which is the silent stall the queue exists to kill. Notice holds carry no pending action, so acknowledging them is the action.

The queue is derived from the durable record, never stored beside it — it cannot drift, and it survives restarts. Park work, walk away, resolve the batch when you return.

11 · Repos — the repository is the unit ⌘4

Every repository Parley has ever worked appears in the sidebar with honest counts — plans needing attention, open backlog items, proposals waiting. Four tabs per repository:

Overview

The repository's plans in flight, the holds waiting on you for this repo (each opens its exact control), the foreman (§12), and a New review button that starts a codebase review pre-aimed here.

Backlog

The repository's durable worklist. Items arrive three ways: confirmed review findings file directly as open; accepted risks are ingested from dispositions; and Stow — a gated sweep you trigger on a session — files softer material as proposed items and candidate learnings for your triage. The lifecycle:

proposed ─ Confirm ─→ open ─ selected into a plan ─→ planned
                       │                                │
                       │                     plan completes / lands
                       │                                ↓
                       ├─ Close ──────────────→ closure proposed ─ Close ─→ done
                       └─ Drop → dropped                └─ Reopen → open
  • Confirm / Discard triage proposals; Blocked by… records ordering between items.
  • Close on an open item records work that is already done — verified by a foreman read, or done outside Parley — without the trail lying that it was "dropped".
  • Completing a plan never closes items silently: it files closure proposals you confirm or reopen. Closed and dropped items stay on the record with their full trails; a recurrence files fresh rather than reopening them.

Plans

Every plan for this repository across all sessions, in one table. A plan opens in place — the full record: milestones, run activity, verify output, reviews, and the same approval gates you'd have in the session view, reading from the same ledger. The origin-session link (↗) jumps to the session that produced it; both surfaces keep their place.

Learnings

Repository-specific knowledge distilled by stow and confirmed by you — conventions, gotchas, decisions. Confirmed learnings ride every new plan's brief for that repository, so the planner starts warned. Retire a learning to stop it riding; it is never deleted.

12 · The foreman

The proposing role: one gated read of a repository's open backlog that files a plan proposal for you to decide. The foreman has proposal power only — it decides nothing, and backlog text is framed to it as records under review, never as instructions.

Ask the foreman (on the repository's Overview) dispatches one read. The attempt is recorded before dispatch, so a crash is a recorded failure, not a vanished spend. The proposal that comes back carries:

  • a title and rationale, and the selected items — validated against the live backlog, resolved to live titles;
  • deferrals with reasons — items it read and chose not to batch, each with why (often: "already landed — close as verified");
  • a staleness line if the backlog moved after the read — "3 items arrived after this proposal" — so you decide with eyes open;
  • a draft operator note, attributed to the foreman.

Accept into a plan opens the plan dialog prefilled — repository, items, isolation, note, anchor session. Creating that plan is the acceptance: the plan row, the items' flip to planned, and the accepted stamp are one transaction, so there is no moment where a plan runs while its proposal still reads pending. Reject… records the reason. A newer run supersedes the older proposal rather than erasing it; failed reads keep their spend and their reasoning — a read that honestly concludes "nothing to plan" shows its per-item verdict under the panel's idle line instead of dying in a toast.

13 · Self-update dev mode

When Parley runs from its own checkout (npm run dev), it knows which repository it is — and the loop closes on itself.

  • Plans on Parley's own repo are worktree-only. The dialog greys the in-checkout option, and the engine refuses it at creation and again at execution. An agent writing into the live app's source under it is the one uncontrolled case.
  • Landing runs the gate. When such a plan lands, Parley automatically runs its own npm run verify and then npm run build on the result. The gate fails closed: any anomaly — failing checks, a timeout, a quit mid-run — is a red row, never a shrug. Red flags the landed plan through the ordinary landed-but-verification-failed hold.
  • Green is an offer, not an act. "A new Parley build is verified" joins the holds queue with inline controls: Relaunch confirms the costs — the app quits and restarts into the fresh build, running panes close, the npm run dev terminal ends — then boots the version Parley just built of itself. Not now records the decline. Every attempt, outcome and decision is a durable row.

Two channels, deliberately distinct. This loop upgrades the dev checkout — the factory. An installed Parley.app from a .dmg is a frozen snapshot: it stays on its old version until you run npm run package:mac and reinstall. Packaged-app self-update is a separate, much later project.

15 · Mock mode

PARLEY_MOCK=1 npm run dev replaces both CLIs with deterministic mock adapters: every flow is walkable, nothing consults a model, no quota is spent. Because mock output is structurally identical to real output, the substitution is made unmissable — a hazard-striped banner under the toolbar, a mock tag on every session, plan and loop, and a NOT REAL WORK header on exported reports.

Two honest caveats. Mock mode is not quite read-only: a write-capable milestone writes one placeholder file, so the pipeline's tree checks stay exercisable. And mock plans never land — by invariant — so the landing-and-self-update leg cannot be walked in mock mode; integration tests cover it instead.

16 · Troubleshooting

Terminals will not start

posix_spawnp failed on every pane — including a plain shell — means node-pty's spawn-helper binary is missing or not executable. Parley detects this at startup and says so. The fix:

npm run rebuild

The CLIs are reported missing but work in Terminal

macOS starts GUI apps with a minimal PATH. Parley reads your login shell's PATH at startup to correct this; if your PATH is set somewhere the login shell doesn't read, launching Parley from Terminal once inherits the right environment.

A milestone reports "the working tree is byte-for-byte unchanged"

The files it was meant to create already exist — usually left by an earlier attempt — and the executor declined to overwrite them. The approval dialog's preflight warns about exactly this before you spend anything, and offers Adopt & verify instead.

The Electron binary is damaged

npm run fix:electron

17 · Where your data lives

Nowhere else. Sessions, verdicts, findings, dispositions, approvals, plans, loops, backlog, learnings, saved layouts and the whole audit trail live in SQLite under the app's own support directory (~/Library/Application Support/parley/), with execution worktrees beside it. There is no sync, no telemetry, and no remote service. The renderer runs sandboxed with no Node access and a content-security policy that permits no remote origins; everything privileged crosses one validated IPC channel.

Development builds keep a separate record: running from the checkout (npm run dev, marked by a dev chip in the titlebar) uses ~/Library/Application Support/parley-dev/, so a dev build migrating the schema can never brick an installed Parley.app, and the two can run side by side.

A · The ten invariants

The commitments the product is built around — break any of these and it stops being what it is. Stated in full in AGENTS.md.

  1. Subscription CLIs only. Every model call goes through your local claude or codex, signed in to your account. No API-key path, ever.
  2. No --dangerously-* flag, ever. The capability ladder is none → read → write, and there is no rung above it.
  3. Read-only is the default. Sessions never write. Only the audited pipeline and an explicitly write-capable loop can, behind an approval.
  4. Approval is recorded and single-use. Starting the run spends it; running again needs a fresh one.
  5. No agent certifies its own work. The reviewer is never the vendor that wrote the diff; a loop's verifier is a different family from its worker.
  6. Exit conditions are observed, not self-reported. A real command's exit code, or the other vendor's inspection. "The agent said it was done" is not a termination condition.
  7. Caps are enforced by Parley, before dispatch. Hitting one is exhausted, never succeeded.
  8. Everything stays local. SQLite on your machine. No sync, no telemetry, no remote anything.
  9. Dissent is preserved. Disagreement lowers recorded confidence and the objection is stored verbatim.
  10. macOS-native restraint. Hairline rules, small radii, one accent, tabular numerals, system type. No gradients, no decorative AI tropes.
